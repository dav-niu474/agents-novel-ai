# Novel Market Radar · 平台热榜分析 + 选题

写网文不是闭门造车。**先扫市场再开书**会让选题命中率显著提升。这个 skill 负责扫各大中文网文平台的榜单，提取趋势、卖点、子赛道空缺，输出可被 blueprint 直接使用的"市场报告"。

⚠️ 不是替用户做选题。是把市场情况量化呈现，让用户做信息充分的决策。

⚠️ 与 inkos / webnovel-writer / AI-Novel-Writing-Assistant 的差异化：

- inkos 有 radar agent 但只做英文榜单
- webnovel-writer 没有市场分析
- AI-Novel-Writing-Assistant 没有市场分析
- Novel Studio：**专做中文网文平台**（起点 / 番茄 / 晋江 / 刺猬猫 / 知乎盐选）+ 子赛道空缺识别

---

## 1. 何时使用 / 何时不要使用

✅ 使用：
- 开书前用户没思路（"什么题材火 / 该写什么"）
- 开书前用户想验证方向（"解析流现在饱和了吗"）
- 写到中段想看读者偏好（"主角性格内敛是不是太冷了"）
- 用户主动要看竞品（"看看类似的书都怎么写的"）
- 完书后想写下一本，需要选题

❌ 不要使用：
- 用户已经定好题材 → `novel-blueprint`
- 用户想看自己的素材库 → `novel-asset-vault`
- 用户问"这章怎么写" → `novel-chapter-writer`
- 没有联网能力的环境 → 提示用户

## 2. 输入与输出契约

### 输入（必需）
- 用户的扫描意图（题材 / 平台 / 时间窗口）
- 联网能力（web-search / web-fetch）

### 输入（可选）
- `novel.json`（用户已有书，按这本书的方向定向扫）
- 用户给的具体竞品列表（"扫《某某书》的卖点"）

### 输出
- `audit/trends/trend-<YYYYMMDD>.md`（trend 报告主文件）
- `audit/trends/trend-<YYYYMMDD>.json`（结构化数据，便于复用）
- `vault/references/ref-<id>.md`（如用户决定沉淀某段竞品文本作 reference）
- `vault/inspirations/insp-<id>.md`（识别出的子赛道空缺 → 灵感卡）

| 3 | 历史 | 12% | 18% | ↑↑ |
| ... | ... | ... | ... | ... |

- 玄幻 - 解析流：饱和（近 30 天 8 本类似设定，质量参差）

- 都市 - 退役老兵：上升期（近 30 天 5 本，2 本进推荐榜）

### 4.2 竞品分析报告

**适用**：用户问"看看类似的书都怎么写"或给了具体竞品。

**结构**：

```markdown
---
asset_type: trend-report
report_type: competitor-analysis
generated_at: <ISO>
focus: 解析流玄幻
---

# 竞品分析：解析流玄幻

## 头部 5 本（推荐榜 / 月票榜）

### 1. 《<书名>》（作者）
- 平台：起点
- 字数：280 万
- 当前订阅：约 X 万
- 卖点结构：
  - 主角差异化：现代医生穿越（专业知识打底）
  - 金手指：解析 + 改造（不止"看出漏洞"还能"动手改"）
  - 节奏：前 5 章爆发，第 30 章卷末高潮极爽
  - 卖点章节：第 5 / 17 / 30 / 45 章
- 高赞短评关键词：节奏快、智斗、师徒情真
- 风险点：中段第 80 章开始水（差评集中）

### 2. ...

## 共同打法
- 5/5 部作品在第 1 章就让金手指首用（无铺设期）
- 4/5 部作品在第 30 章前完成第一次"反噬"代价暴露
- 5/5 部主角设定都是"现代知识 + 古代修真境界"

## 差异化机会
- 没有作品做"金手指会消失"承诺
- 没有作品做"反派也有解析能力"
- 都市背景的"解析现代物体"切入点空白

## 引用沉淀
建议把以下 3 段沉淀为 vault/references/：
- 《<书名>》第 5 章反杀（学习节奏）
- 《<书名>》第 30 章卷末高潮（学习高潮编排）
- 《<书名>》第 17 章金手指代价首现（学习代价描写）

要沉淀吗？
```

### 4.3 子赛道空缺报告

**适用**：用户想找"还能写"的方向。

**结构**：

```markdown
---
asset_type: trend-report
report_type: niche-opportunity
generated_at: <ISO>
target_genre: 玄幻
---

# 玄幻子赛道空缺扫描

## 方法
1. 列出近 90 天起点 + 番茄玄幻新书 top 100 的子赛道分布
2. 对比读者高赞评论中"想看但没看到"的关键词
3. 排除明显饱和的（近 30 天 ≥ 10 本类似设定）

## 候选子赛道

### 候选 1：金手指会消失
- 现状：起点 / 番茄都没有作品做"明确承诺金手指会失效"
- 读者声音：知乎"为什么修真小说总是越来越无敌"高赞 4.2k
- 写法风险：需要前期就埋好"消失"的铺垫，不能虎头蛇尾
- 建议：开书蓝图第 5 节钩子里埋一条"第 200 章金手指消失"

### 候选 2：反派也有解析能力
- 现状：解析流主角都是孤悬，反派从不解析
- 读者声音：评论区常见"反派如果也有同样能力会怎样"
- 写法风险：可能让主角金手指失去差异化
- 建议：反派的解析能力是"逆向"——解析后只能反制不能学习

### 候选 3：唐朝武将转生
- 现状：起点 / 番茄近 30 天 0 本，晋江有 2 本（女频武将）
- 读者声音：唐朝古装剧近年回暖，文化背景吃读者
- 写法风险：唐朝史实考据要求高
- 建议：可考虑"安史之乱"时期，戏剧冲突丰富

## 综合
3 个方向选 1 个进入 blueprint 定盘？
```

## 5. 工作流

### 工作流 A：广度扫描（用户没思路）

触发：用户说"什么题材火 / 选题 / 该写什么"。

```
1. 询问扫描范围：
   - 平台（起点 / 番茄 / 晋江 / 刺猬猫 / 知乎 / 全部）
   - 时间窗口（近 30 天 / 近 90 天 / 半年）
   - 用户偏好（男频 / 女频 / 不限）

2. 构造 web_search query 系列
3. 抓取榜单数据（控制次数：单个平台不超过 3 次抓取，避免拖慢）
4. LLM 分析归纳：
   - 题材占比
   - 子赛道分布
   - 升 / 平 / 降趋势
5. 输出题材热度报告（4.1）→ audit/trends/trend-<date>.md
6. 提示用户："建议下一步进入 blueprint 定盘"
```

### 工作流 B：定向竞品分析

触发：用户说"看看《某某书》怎么写的 / 解析流的头部都怎么开局 / 竞品分析"。

```
1. 解析用户给的方向（题材 / 子赛道 / 具体书名）
2. web_search 找 top 5-7 部头部作品
3. web_fetch 拿每部书的：
   - 简介
   - 标签
   - 第 1 章前 500 字
   - 评论区高赞短评（取前 5 条）
4. 分析卖点结构 + 共同打法 + 差异化机会
5. 输出竞品分析报告（4.2）
6. 提示沉淀建议（vault/references/）
```

⚠️ 竞品文本抓取必须遵守：

- 不全文抓（≥ 30 字片段属于 fair use 学习用）
- 必须注明出处（作者 / 平台 / URL）
- 不允许 chapter-writer 的 compose 阶段直接使用 references（详见 asset-vault R2）

### 工作流 C：子赛道空缺扫描

触发：用户说"还有什么能写的 / 哪个方向没人做 / 蓝海"。

```
1. 询问目标题材（必填）
2. 扫该题材近 90 天新书 top 100，统计子赛道分布
3. 扫读者评论 + 知乎 / B 站相关讨论，提取"想看没看到"信号
4. 交叉对比，列出 3-5 个候选空缺
5. 评估每个空缺的：
   - 现状（饱和度）
   - 读者声音
   - 写法风险
   - 建议切入方向
6. 输出空缺报告（4.3）
7. 让用户挑 1 个进入 blueprint
```

### 工作流 D：中段读者偏好对照

触发：用户写到中段说"我现在的写法读者爱看吗 / 主角设定是不是太冷"。

```
1. 读 novel.json + blueprint.md 确定题材 + 主角风格
2. 扫该题材近期高订阅书的主角风格分布：
   - 内敛 / 张扬
   - 慢热 / 上来就爽
   - 智斗 / 硬刚
3. 对比当前书的设定，给出"是否同向 / 偏差有多大"
4. 输出对比报告（不强求改，只是信息）
```

⚠️ 这一步**不替用户改**。只给数据。

### 工作流 E：完书复盘 + 选题下一本

触发：用户说"这本书快完结了 / 写完了 / 下一本写什么"。

```
1. 读当前书的 audit/reports/full-book-audit.md（如有）
2. 扫当前题材最新趋势（同工作流 A）
3. 结合作者经验：
   - 当前书最被读者爱看的章节类型 → 下一本可以延续
   - 当前书的硬伤（如金手指设定崩坏）→ 下一本避开
4. 给出 3 个候选方向（同 blueprint 工作流 A 的灵感工坊）
5. 转 blueprint 进入定盘
```

## 6. 关键规则

### R1：只给数据，不替决定

题材选择 / 主角设定 / 金手指 永远是用户的决策。market-radar 的输出是"信息层"。

### R2：fair use 引用

竞品分析必须：
- 单段引用 ≤ 30 字 / ≤ 200 字（视上下文）
- 注明作者 / 书名 / 平台 / URL
- 不全文复制
- chapter-writer 不直接使用

### R3：联网失败不要硬撑

如果 web_search / web_fetch 失败：
- 提示用户当前不能联网
- 询问是否手动提供数据（用户贴几本竞品的简介）
- 或建议先做内部数据驱动的（vault/inspirations 检索）

### R4：报告必须有时间戳

trend report 标 generated_at。市场数据 30 天就过时，太老的报告自动建议重扫。

### R5：trends 目录归档

旧报告不删除，归档在 `audit/trends/`。第二次扫时新建 trend-<新日期>.md，旧的保留供对比。

### R6：从竞品沉淀走 vault

competitor-analysis 报告里建议沉淀的内容**必须经过 asset-vault skill 落盘**，不直接写 vault/references/（避免双权威）。

### R7：不抓盗版 / 不抓收费章节

只抓公开免费的：简介、第 1 章免费部分、评论。**不抓 VIP 章节内容**。

## 8. 错误处理

| 错误场景 | 处理方式 |
|---------|---------|
| 无联网能力 | 提示用户，问是否手动贴数据 |
| 平台反爬 / 429 | 退避重试 1 次，再失败就让用户自己粘贴关键信息 |
| 用户给的竞品名 / URL 不存在 | 询问是否拼写错了 / 让用户给更准确的名字 |
| 抓到的内容太少（< 5 本书） | 警告样本不足，结论仅供参考 |
| 用户希望 market-radar 直接帮"开书一条龙" | 拒绝。market-radar 只输出报告，开书要 blueprint 接手 |
| 时间窗口太长（> 1 年） | 警告时效性，建议聚焦 90 天内 |
| 用户希望 market-radar 抓 VIP 收费章节 | 拒绝（R7） |
